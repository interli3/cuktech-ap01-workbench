# 04 救机与回原厂

## 0. 先判断属于哪种情况

救机不是“先刷一遍再说”。先看屏幕在米家里的状态：

| 状态 | 能不能软件救 | 走哪一节 |
|---|---|---|
| 在线，自定义画面不刷新/服务挂了 | 能 | 情况 A |
| 在线，但被升到了 0041 | 能，先降级 | 情况 B |
| 在线，版本是 0031 但界面乱了 | 能，回原厂 | 情况 C |
| 离线，米家看不到，但之前能配网 | 先尝试重新配网/断电重启 | 情况 D |
| 彻底离线、配网失败、反复重启 | 软件救不了 | 售后/拆机，见情况 E |
| 已经是 0055 | 不建议任何写入 | 见 [03](03-0055-未知状态.md) |

**唯一硬边界：设备必须还能在米家在线，电脑才能通过云通道发命令。**
彻底离线时，本仓库的脚本一条也发不进去。

## 情况 A：屏幕在线，但画面不刷新

最常见，通常不是固件坏了，是电脑端服务或网络的问题。

1. 在电脑上访问 `http://电脑IP:18766/health`：
   - `ok: true` 且在涨，说明服务活着；
   - 连不上，说明服务没起或端口被占。
2. 重启显示服务：

```bash
# 如果用的是任务计划
schtasks /End /TN "AP01-Display"
schtasks /Run /TN "AP01-Display"

# 如果是手动起的
taskkill /F /IM pythonw.exe
python tools/display_service.py
```

3. 看屏幕是否恢复。加载器每秒请求一次，正常 1～2 秒内就会换图。
4. 还不行，检查防火墙是否放行 `18766`，以及屏幕 IP 是否变了。

不要因为画面不刷新就刷固件。先确认 `/health` 和防火墙。

## 情况 B：在线，但版本是 0041

0031 的正常重刷会失败，因为 0041 的写入器会取反首字节。
先按 [02-降级-0041到0031.md](02-降级-0041到0031.md) 降回 0031，
再走情况 C 或重新装加载器。

不要直接把 0031 加载器往 0041 上发。

## 情况 C：在线，0031，但界面乱了

用回原厂脚本，把干净的 0031 再刷一遍。默认是 dry-run：

```bash
python tools/restore_factory.py --did 你的设备DID
```

确认输出里的 `mode` 是 `DRY_RUN`、`target` 是你的设备、`bytes` 是 6,804,520，
再加 `--go`：

```bash
python tools/restore_factory.py --did 你的设备DID --go
```

它会：

1. 确认 DID 在 `allowed_dids` 白名单里（如果配了）；
2. 确认设备在线、型号匹配、当前是 0031 且 OTA idle；
3. 在 443 起 HTTPS，只允许电脑和目标屏幕访问；
4. 发一次 `miIO.ota`，使用正常未签名 OTA；
5. 等设备下载、重启、运行时间归零、版本仍是 0031；
6. 写一份事务日志到 `run/`。

一次只允许一台。写命令只发一次，失败不自动重试。

## 情况 D：离线，但之前能配网

1. 断电 10 秒再上电；
2. 在米家里看设备是否回到在线；
3. 如果显示配网模式，按原厂流程重新配网（2.4G Wi-Fi，不要用 5G）；
4. 配网成功后读 `miIO.info`，确认版本和 `life`；
5. 再决定是回原厂还是继续用。

不要在离线状态下反复发 OTA 命令。命令发不进去，还会把事务文件弄乱。

## 情况 E：彻底离线，配网失败

软件路线到此为止。可能的原因：

- 固件分区损坏，启动不了网络栈；
- 硬件/屏幕排线问题；
- 设备进入了无法恢复的模式。

本仓库没有 0055 的救砖点位，也没有拆机短接方案。
建议联系酷态科售后，如实说明“升级后无法开机/无法配网”。
不要为了“试试看”反复刷入不同版本。

## 救机包应该有什么

本仓库的 `firmware/` + `tools/` 就是救机包的最小集合：

| 文件 | 用途 |
|---|---|
| `firmware/原厂_0031.bin` | 恢复主文件（0031 不查签名） |
| `firmware/原厂_0041.bin` | 比对/确认版本 |
| `firmware/降级用_0031_首字节预反转.bin` | 0041 降级传输 |
| `firmware/加载器_0031_18765_硬件监测.bin` | 硬件监测模式 300 帧长连接 |
| `firmware/加载器_0031_18766_账户余额.bin` | 账户工作台模式 300 帧长连接 |
| `firmware/备用_0031_60秒取图.bin` | 60 秒取图旧版，备用 |
| `firmware/备用_18766_60秒取图.bin` | 60 秒取图旧版（账户工作台模式），备用 |
| `tools/restore_factory.py` | 回原厂 |
| `tools/downgrade_0041_to_0031.py` | 0041 降级 |
| `tools/install_loader.py` | 装加载器 |
| `firmware/SHA256SUMS.txt` | 全部文件的哈希 |

把整个仓库复制到 U 盘/网盘，就是一份离线救机包。
不要只存 `.bin` 不存脚本，也不要改文件名后不更新哈希。

## 事务文件规则

每次写设备都会创建一个 `.jsonl` 事务文件。它的作用是**防重跑**：

- 文件存在 = 这次已经发过命令，不能再发；
- 不要删文件来“重试”；
- 要重试，先读日志确认设备状态，再新建一个事务文件（改 `journal_dir` 或文件名）；
- 日志里只记白名单字段，不记云端响应、请求头或凭据。

## 最后一条

**能在线，就有很大机会救回来；不能在线，就不要靠软件折腾。**
先保命，再谈自定义。
