# 02 降级：从原厂 0041 到原厂 0031

本章是**已经真机成功两次**的路线。它只解决一件事：把 0041 变成 0031。
不涉及 0055；0055 是升级，不是降级，见下一章。

> 风险提示：这是对设备分区写入固件。中途断电、电脑休眠、防火墙拦截、
> 端口被占用都可能导致设备离线。开始前先读完本章和
> [09-风险与未验证.md](09-风险与未验证.md)。

## 1. 开始前的硬条件

**先跑这一条只读体检命令**，它不会写设备，会把下面大部分条件一次性查清楚：

```bash
python tools/check_device.py
```

正常输出长这样（数值每次不同）：

```
找到 1 台 AP01：
   DID 1234567890   局域网 IP 192.168.1.x   在线
      型号 njcuk.enstor.ap01   固件 1.0.2_0041   运行秒数 life=3210   OTA=['idle']
      → 可以降级：当前是 0041 且空闲，按 docs/02 走。
```

把输出里的 DID 和局域网 IP 填进 `config.json` 的 `device.did` / `device.device_ip`。
看到别的提示就按提示走，别硬来。

| 条件 | 怎么确认 |
|---|---|
| 设备在线 | 体检命令会显示「在线」；米家里也能看到 |
| 当前是 0041 且 OTA 空闲 | 体检命令直接打印固件版本和 `OTA=['idle']` |
| 电脑和屏幕同网段 | 命令行 `ping 屏幕IP` 能通 |
| 电脑 443 端口空闲 | `netstat -ano | findstr :443` 没有别的程序在监听 |
| **用管理员身份开终端** | 443 是特权端口，普通权限会报「权限不足」；右键终端选「以管理员身份运行」 |
| 上游仓库和登录态就绪 | 见下面「小米登录态怎么来」 |
| 只操作一台 | 账号里有多台时，一次只填一个 DID |

### 小米登录态怎么来

降级脚本要借上游工具连小米云。按顺序跑下面这几条（登录只需第一次）：

```bash
git clone https://github.com/andy-JustSayWhen/cuktech-ap01-firmware-tools.git
cd cuktech-ap01-firmware-tools
python -m pip install -r requirements.txt
python app/ap01_official_firmware.py login
```

最后一条会打印一张二维码图片的路径，用**绑定了这块屏的那个米家账号**
扫码并在手机上确认。成功后会在上游仓库生成 `env/mi-cloud.env`，
里面是三项登录态（`CUKTECH_MI_USER_ID` / `CUKTECH_MI_PASS_TOKEN` /
`CUKTECH_MI_DEVICE_ID`）。

⚠️ 这个文件**只留在你自己电脑上**：上游仓库有它自己的 `.gitignore`，
本仓库也不会读取它的内容、更不会提交。如果 `check_device.py` 提示
「没找到小米登录态」，回到上游目录重新跑一次 `login` 即可。

不要用「找到的第一个网卡地址」当绑定地址。Clash 之类会把 `198.18.*`
虚拟网卡排在最前，设备根本回不来。脚本用「到目标屏幕 IP 的实际路由」
决定绑定地址，这是故意的。

## 2. 生成传输固件

```bash
python tools/patch_firmware.py preinvert \
  --in firmware/原厂_0031.bin \
  --out build/0031-transport.bin
```

期望输出里能看到：

```
首字节 0x42 -> 0xbd（设备写入器会再取反一次）
SHA256 828adbb3ba6087765e9888f40c42177104b4a327088d8e9a2847a35ee61b48de
MD5    5b6e53f94fd19b4d458785885620e412
```

这两个哈希必须和 `docs/01` 里的表一致。不一致就说明文件被换过，停。

如果直接拿仓库里现成的 `firmware/降级用_0031_首字节预反转.bin`，
可以跳过这一步，但建议自己算一遍哈希确认。

## 3. 填配置

`config.json` 里和降级有关的字段：

```json
{
  "device": {
    "did": "你的设备DID",
    "model": "njcuk.enstor.ap01",
    "hw_ver": "BL618-BL4",
    "device_ip": "你的屏幕IP"
  },
  "network": { "bind": "你的电脑局域网IP" },
  "upstream": { "repo": "上游仓库本地路径" },
  "firmware": {
    "stock_0031": "firmware/原厂_0031.bin",
    "downgrade_0031": "firmware/降级用_0031_首字节预反转.bin"
  },
  "paths": { "journal_dir": "run" }
}
```

`device_ip` 用来做身份核对，必须和云端返回的 `localip` 一致。
不一致脚本会拒绝执行。

## 4. 先看计划，不写设备

```bash
python tools/downgrade_0041_to_0031.py
```

输出类似：

```json
{
  "mode": "OFFLINE_PLAN_ONLY",
  "target": "你的DID",
  "other_target_forbidden": true,
  "bytes": 6804520,
  "wire_md5": "5b6e...",
  "expected_stored_sha256": "8a72...",
  "max_mutating_dispatches": 3,
  "physical_success_verified": false,
  "risk": "May require pairing reset; no guaranteed hardware or remote rescue"
}
```

这一步会检查：

- 原厂 0031 的 SHA-256 是不是 `8a721fc8...`；
- 传输文件是不是首字节预反转、其余字节完全一致；
- 传输文件的 SHA-256/MD5 是不是 `828adbb3...` / `5b6e53f9...`；
- 事务文件是否已经存在（存在就拒绝重跑）。

## 5. 真正执行

确认设备就在手边、不会断电、米家账号能重新配网，再执行：

```bash
python tools/downgrade_0041_to_0031.py --execute-once
```

脚本会做这些事，顺序不能变：

1. 通过小米云读设备列表，确认目标 DID 唯一、在线、型号匹配；
2. 读 `miIO.info` 和 `miIO.get_ota_state`，要求 `1.0.2_0041` 且 `idle`；
3. 用 UDP `connect` 选路由，得到电脑的局域网地址；
4. 在本机 443 起 HTTPS 固件服务，只允许电脑自己和目标屏幕 IP 访问；
5. 本地自测下载一遍，确认文件字节完全一致，且这次自测不算“设备已下载”；
6. 再次确认设备还是 0041 idle；
7. **发一次** `ota.downgrade {"downgrade": 1}`；
8. **发一次** `miIO.ota`，把传输文件 URL、MD5、长度交给设备；
9. 设备开始下载，通常完整下载三轮，每轮 6,804,520 字节；
10. 期间只读轮询；读失败不关服务、不重发写命令；
11. 等“完整下载完成 + OTA 连续空闲 30 秒”；
12. **发一次** `miIO.recovery {"module": "app"}`；
13. 继续只读观察最多 180 秒，看到 `1.0.2_0031` 才记录成功。

整个过程最多 3 个写命令，每个只发一次。事务文件里会逐条记录，
包括 `dispatch_intent`、`dispatch_result`、`observed`、`version_0031_observed`。

## 6. 成功长什么样

**验收命令就是开头那条，再跑一遍：**

```bash
python tools/check_device.py
```

看到下面三样，才算成功：

- `固件 1.0.2_0031`、`型号 njcuk.enstor.ap01`；
- `life`（运行秒数）是一个很小的数字，隔一分钟再查会变大，说明设备确实重启过；
- `OTA=['idle']`。

**不要用命令回执判断成功。** 真机有一次 `miIO.recovery` 回执是
`accepted=false`，设备随后查询超时、离线，但几十秒后自己重新上线，
版本已经是 0031。回执只说明「云通道有没有当场确认」，不等于设备没执行。

## 7. 失败和中断怎么处理

事务日志在 `run/downgrade-0041-to-0031.jsonl`（由 `config.json` 的
`paths.journal_dir` 决定）。遇到任何异常，**先打开这个文件**看最后几行，
里面按顺序记着 `dispatch_intent`、`dispatch_result`、`observed`、
`version_0031_observed`，能看出卡在哪一步。

| 现象 | 含义 | 处理 |
|---|---|---|
| 只读查询失败 | 网络/云通道暂时不可用 | 脚本会保持固件服务、等恢复；不要手动关 |
| 提示「权限不足」或 443 被占 | 没用管理员身份 / 别的程序占了端口 | 换管理员终端；`netstat -ano | findstr :443` 查占用 |
| 提示「没找到小米登录态」 | `env/mi-cloud.env` 没生成或过期 | 回上游目录重跑 `python app/ap01_official_firmware.py login` |
| 设备离线 | 可能在重启 | 等 1～2 分钟；不要重复发恢复命令 |
| 版本仍是 0041 | 本轮没成功 | 脚本停止；不要删事务后原地重跑 |
| 事务文件已存在 | 之前跑过一次 | 先读事务日志确认设备状态；要重试就换新目录，不要删旧文件 |
| 需要重新配网 | 恢复后网络配置丢了 | 在米家按正常流程重新配网，不要拆机 |

绝对不要做的事：

- 不要删事务文件来「绕过防重」；
- 不要在设备下载中途关电脑、关 Wi-Fi、休眠；
- 不要同时对多台设备执行；
- 不要在 0055 上套这套流程。

## 8. 两次真机时间线（脱敏）

> 这一节是当时的历史记录。开发时手上有两台设备，所以各跑一种模式；
> **你只需要一台**，两种模式怎么换见 [07-一块屏的两种模式.md](07-一块屏的两种模式.md)。

| 时间 | 当时的设备 | 结果 |
|---|---|---|
| 20:12:06 | 设备 1（后来跑模式 A） | 只读返回 `1.0.2_0031`，life 121 秒 |
| 20:13:18 | 设备 1 | 仍为 0031，life 增长到 193 秒 |
| 22:16:41 | 设备 2（后来跑模式 B） | 发出 `ota.downgrade` 和 `miIO.ota` |
| 22:18:52 / 22:21:07 / 22:23:23 | 设备 2 | 完整下载三轮 |
| 22:24:21 | 设备 2 | 发出唯一一次 `miIO.recovery`，回执 `accepted=false` |
| 22:26:25 | 设备 2 | 自己重新上线，返回 `1.0.2_0031`，life 124 |
| 22:26 之后 | 设备 2 | 再读仍为 0031，life 145 |

设备 1 全程没被碰；两次执行使用不同的 DID、事务文件和端口。

## 9. 降完做什么

降级只把系统变成 0031，屏幕上还是原厂界面。**不要直接去装加载器**，
顺序是：

1. 按 [README 第 3 步](../README.md#3-起你选的那个显示服务必须在装加载器之前)
   先起你选的那种模式的显示服务，并在浏览器里确认 `/health` 和 `/screen.gif`；
2. 再按 README 第 4 步跑 `install_loader.py` 装加载器——它会拿服务做验证，
   服务没起一定被拒；
3. 两种模式怎么选、怎么换，见 [07-一块屏的两种模式.md](07-一块屏的两种模式.md)。

如果降完发现屏幕在线但显示异常，先走
[04-救机与回原厂.md](04-救机与回原厂.md)，不要继续刷。
