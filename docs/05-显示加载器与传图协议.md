# 05 显示加载器与传图协议

## 1. 加载器是什么

加载器不是“另一个 App”，它是一份 0031 固件：

- 保留原厂的启动、网络、屏幕驱动；
- 在里面塞了一小段代码，让屏幕定时向电脑请求 GIF；
- 装好后版本号仍然是 `1.0.2_0031`，但屏幕内容由电脑决定。

所以装加载器 = 刷一次 0031 固件，不是装驱动。
装之前必须先降到 0031，0041 装不上。

## 2. 从 60 秒到 1 秒：中间踩过的坑

### 2.1 原版加载器

最早的加载器每 60 秒请求一次 `/screen.gif`。
用户插上手机，功率 5 秒就采到了，但屏幕要等近一分钟才变。
看起来像“功率读不到”，其实是画面链路太慢。

### 2.2 只改定时常量

把固件里的 60000ms 改成 1000ms，只差 7 个字节（含 CRC）。
真机确实开始约每 1.002 秒请求一次，但日志里仍有 7 秒、24 秒、31 秒的停顿，
中位数好看，最长停顿很难看，用户还是会看到“数据已过期”。

### 2.3 短连接方案失败

试过省略 `Content-Length`、由电脑主动关闭写方向，减少屏幕端连接回收压力。
短期连续，239 秒后仍出现约 24 秒停顿。放弃。

### 2.4 四帧、五帧也不够

把多张 GIF 放进一个 HTTP 响应，每块固定 24576 字节：

```
offset 0..3    小端 GIF 长度
offset 4..N    GIF 字节
剩余部分       补零到 24576 字节
```

四帧方案在 426 秒里中位 1 秒，但最大 5.257 秒；
五帧方案 180 秒内最大 1.003 秒，后来还是出现 7 秒停顿。
短期通过不算通过。

### 2.5 300 帧长连接

把每批从 5 张扩大到 300 张，在一条 HTTP 连接里逐秒发送 5 分钟。
设备仍然只保存三个 GIF 槽和 4KB 网络缓存，不会一次缓存 300 张。
收齐 300 块后主动正常结束，再重新连接。

最终硬件监测模式实测：

- 330.623 秒发送 331 张；
- 中位间隔 0.999983 秒；
- 最大间隔 1.019415 秒；
- 没有超过 3 秒的空档；
- 110 次电脑健康采样全部通过；
- 设备第二次请求报告 `g=300, a=299, e=0`。

## 3. 为什么必须把网络线程拆出去

原厂固件的事件回调和 UI 在同一个线程。同步等 HTTP 会把旋钮和点按拖住。
现象是：图在更新，但旋钮不动、点按很慢。

修正方式：

- 原厂事件回调只负责“触发一次任务”并立刻返回；
- 网络线程有自己的 HTTP 上下文、URL 副本和 4096 字节收包区；
- 忙标记放在 tmpfs，已有任务时不重复创建；
- 线程 `detached`，16KB 栈；
- UI 仍然只在原厂线程里应用完整图片。

验证方式很土但有效：让服务器快速返回 503，屏幕显示 waiting for bridge，
旋钮恢复；说明网络等待确实会拖住原厂事件处理。拆线程后，
即使出现过期提示，旋钮和点按也正常。

## 4. 三个 GIF 槽和诊断参数

设备内存里只有三个槽：

1. 当前正在发布的槽；
2. UI 已经确认的槽；
3. 新下载的槽。

新下载的槽不能覆盖前两个。只有同时满足：

- HTTP 200；
- 长度有效；
- GIF 头是 `GIF89a`；
- 末尾有 `0x3B`；
- 320×240、至少两帧；

才发布。

下一次连接会带四个诊断参数：

| 参数 | 含义 |
|---|---|
| `v` | 协议版本，当前是 2 |
| `g` | 最近收到的 generation |
| `a` | UI 已确认的 generation |
| `e` | 上一次传输错误码 |

电脑端用它们区分“服务器发了”和“设备真的收了”。
`/health` 会显示最近一次 `v/g/a/e`，这是验收的关键证据，不是装饰。

## 5. 改端口：只改 URL 和 CRC

加载器里写死了两处 URL：

```
http://电脑IP:18765/live.bin
```

账户工作台模式要用 18766，就把两处都换成等长字符串，再重算末尾 CRC：

```bash
python tools/patch_firmware.py patch-url \
  --in firmware/加载器_0031_18765_硬件监测.bin \
  --out build/loader-18766-live.bin \
  --old http://192.168.1.160:18765/live.bin \
  --new http://192.168.1.160:18766/live.bin
```

> 仓库里**已经放好了 18765 和 18766 两个成品加载器**，正常部署不需要自己做这一步。
> 只有当你想用第三个端口（比如 18767）、或者要换电脑地址时，才需要照上面这样
> 自己生成一份。换完记得把 `config.json` 的端口和 `firmware.loader` 一起改掉。

规则：

- 新旧 URL 长度必须完全一致，否则脚本拒绝；
- 只替换完全匹配的字节，不做模糊匹配；
- 替换后对“除末尾 4 字节外的全部内容”算 CRC32（初值 `0xFFFFFFFF`，结果再异或 `0xFFFFFFFF`），小端写回末尾；
- 新旧文件长度相同，通常只差 6 个字节：两个端口数字 + 4 字节 CRC。
- 用仓库里的硬件监测模式长连接固件跑这条命令，得到的 SHA-256 应该正好是
  `cd79f6863db8df8ee4b0bb24753a4cd549f904fa69f84458585c219b6b1e8343`，
  和 `firmware/加载器_0031_18766_账户余额.bin` 完全一致。

仓库里的预编译加载器写死了电脑地址 `192.168.1.160`。如果你的电脑不是这个地址：

- 最省事：把电脑的局域网地址设成 `192.168.1.160`（静态），直接能用；
- 地址长度相同：用上面的 `patch-url` 换成你的地址；
- 地址长度不同：不能等长替换，需要重新编译加载器，或者把电脑设成一个
  与 `192.168.1.160` 等长的静态地址。

## 6. 安装加载器

```bash
python tools/install_loader.py             # 离线检查
python tools/install_loader.py --execute-once
```

安装前会核对：

- 目标 DID 唯一、在线；
- 型号 `njcuk.enstor.ap01`、硬件 `BL618-BL4`；
- 当前固件 `1.0.2_0031`；
- 设备局域网 IP 和配置一致；
- 电脑到设备的实际路由等于 `network.bind`；
- 显示服务 `/health` 正常；
- `/screen.gif` 是合法 GIF、320×240、至少两帧；
- OTA 状态 `idle`；
- 镜像 SHA-256 和配置一致、文件头是 `BFNP`；
- 事务文件不存在。

安装过程：

1. 完整传输 6,804,520 字节；
2. 设备进入 `installed/100`；
3. 暂时离线；
4. 重新上线，版本仍是 0031，`life` 归零，`idle/101`；
5. 主动请求 `/live.bin`；
6. 事务日志记录 `loader_request_and_reboot_observed`。

下载末尾可能出现一次 `ConnectionResetError`，这是设备主动关闭 TLS 连接，
不能单独判定失败。以“重新上线 + 运行时间归零 + 请求新接口”联合判断。

## 7. 验收看什么

不要只看“任务 Running”或“下载 100%”。按顺序看：

1. `/health` 的 `ok` 是 true；
2. `requests` 在增长，`median_request_interval` 接近 1 秒；
3. `device_diagnostic.g` 接近 300、`a` 接近 299、`e` 是 0；
4. 屏幕上真的在换图（拔插充电线看功率变化）；
5. 旋钮和点按不卡。

四条都成立，才算加载器真的工作。
