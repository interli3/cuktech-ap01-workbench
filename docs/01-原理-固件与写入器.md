# 01 原理：固件、写入器和为什么 0031 是钥匙

## 1. 设备是什么

酷态科 AP01 是一块带 320×240 彩色屏的桌面充电器/扩展坞。屏幕由一颗
`BL618-BL4` 芯片驱动，设备型号字符串是 `njcuk.enstor.ap01`。
原厂固件通过米家 OTA 下发，屏幕上的内容由固件里的 UI 绘制。

我们要做的，是把原厂固件换成一个“会从电脑拉图”的版本：
屏幕每秒向电脑要一张 320×240 的 GIF，电脑想画什么就画什么。

## 2. 三个固件版本

| 版本 | 文件大小 | 说明 |
|---|---:|---|
| `1.0.2_0031` | 6,804,520 字节 | 老版本，第三方加载器的目标版本，不检查签名 |
| `1.0.2_0041` | 6,769,704 字节 | 新版本，写入器行为变了，但还能降回 0031 |
| `1.0.2_0055` | 6,389,800 字节 | 云端最新版，签名闸门更严，**不可逆，不要刷** |

固件开头 4 个字节是 `BFNP`，末尾 4 字节是 CRC32（小端）。
这两个特征在补丁和校验里都会用到。

## 3. 0041 的写入器到底做了什么

这是整个项目最关键的一条发现。

0041 的写入器在接收固件时，会先把**第一个字节取反**：

```
收到 0x42 -> 写入时变成 0xBD
正常成功收尾时，再翻回 0x42
```

问题在于：原版 0031 在“签名拒绝”分支可能提前退出，收尾流程没走完，
首字节就留在取反状态。设备重启后恢复校验读到的镜像首字节是错的，
CRC 也对不上，于是判定失败，版本仍然是 0041。

所以直接发原版 0031 不行，要**预反转**：

```
原版 0031 首字节 0x42
发送前改成 0xBD
设备写入器再取反一次 -> 0x42（正确）
即使收尾报错，落盘镜像也和原版逐字节一致
```

这就是“降级钥匙”。它不是隐藏命令，也不是改分区，只是利用了写入器
“先取反、成功再翻回”的行为。

预反转只改第一个字节，其他字节必须完全不动。`tools/patch_firmware.py preinvert`
会检查这一点，并打印 SHA-256 和 MD5。

## 4. 为什么 0031 能装第三方加载器

0031 的加载器只认精确的 `njcuk.enstor.ap01 / 1.0.2_0031`。
它通过正常的**未签名 OTA** 安装，不需要首字节预反转：

- 设备完整下载 6,804,520 字节；
- 进入 `installed/100`；
- 重启，运行时间归零；
- 重新上线后版本仍是 0031，OTA 状态 `idle/101`；
- 主动向电脑请求图片。

0041 不能直接装这个加载器，因为加载器里的版本检查和 0041 不匹配。
所以顺序必须是：**先降到 0031，再装加载器**。

## 5. 0055 为什么是另一个故事

0055 不是“更高的 0031”，它是重新编译的版本：

- 文件大小从 6,804,520 变成 6,389,800，布局变了；
- 云端更新日志只提到主题、iPhone 型号识别和“修复已知问题”；
- 没有任何“开放第三方固件/允许降级”的字样；
- 我们从未在 0055 上刷过任何东西，没有真机证据。

0041 的降级钥匙依赖“写入器先取反”的具体行为。0055 的写入器是否还这样、
签名拒绝分支是否提前退出，都没有验证。所以本仓库**不提供**刷 0055 的步骤，
只把它当作“未知状态”记录。详见 [03-0055-未知状态.md](03-0055-未知状态.md)。

## 7. 这套路线成立的前提

1. 设备能在米家在线，能通过小米云 RPC 读到 `miIO.info`；
2. 电脑和屏幕在同一局域网，电脑能起 443 端口给设备下载固件；
3. 设备是 `njcuk.enstor.ap01 / BL618-BL4`，不是别的硬件版本；
4. 一次只操作一台；如果有多台，各自的 DID、IP、端口、事务文件都要隔离。

任何一条不满足，先停下来查清楚，不要靠“再刷一次试试”。
