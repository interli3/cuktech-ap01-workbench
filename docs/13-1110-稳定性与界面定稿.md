## 1. 充电输出：真实读数，不冒充原厂功率

设备通过 MIoT 上报端口信息（service 4 = charger，属性 4/7/9/11 对应
C1/C2/C3/USB-A）。**不要使用较新描述里的总功率属性**：在 `1.0.2_0031`
上读它返回布尔 `false`，把 `false` 当 0 W 会造出假数据。

真机返回的端口整数可以拆出电压和电流：整数的高字节是电压（单位 100 倍取整）、
次高字节是电流。例如 `1529943299` 解出 9.1 V / 4.9 A，与设备原厂详情页一致。
界面用 `V × A` 估算瓦数并显式标注 `≈`；协议档位（如 55 W）不等于此刻持续输出，
不拿来显示。

实现约束：

- 独立后台轮询，约 5 秒一次，网络等待**不进**每秒采集/绘图主循环，
  **也不进**屏幕旋钮事件线程；
- 数据超过 15 秒未更新就显示「不可用」，不用 0 W 冒充读取失败；
- 只有全部端口都返回合法整数才参与计算，布尔值和不完整响应一律拒绝；
- 单口有输出时显示端口名 + 功率 + 电压 + 电流；多口时只显示 USB 合计功率；
- 原厂充电详情页保留不动。

已做实物验收的只有 C1（以及后来切换 C2 的读数反馈）。C3、USB-A 与多口
汇总有代码和渲染测试，**没有逐口插手机真机验收**。

## 2. 界面定稿：用户逐版确认后的最终形态

中间被否掉的方案都保留为过程证据，不要当当前界面：扫描线渐变、浅色平涂、
红色充电卡、过小的转速字号。

最终 320×240 三帧 GIF：

- 顶部 40 像素留给原厂时钟；
- 左上银白充电卡（在 CPU 上方），**功率与电压/电流在同一张卡内**，
  只用一条内部细线对齐，不拆成两个板块；渐变 `#f7fafc → #aeb9c4`，
  白色高光边框、深灰 `#17222d` 主数字，是整页唯一中性色区域；
- 右上帧率卡（在 GPU 上方）——帧率属于 GPU，位置按语义归位；
- CPU 橙 `#ffae0a → #ff6500`，GPU 青蓝 `#16f5ff → #008bff`，
  内存黄绿 `#e4ff0a → #a4ed00`，显存蓝紫 `#99baff → #737bff`；
- CPU/GPU 两张卡统一三层：型号 / 左温度右占用（27 px）/ 细线下左功率右转速（14 px），
  只靠 `W` 和 `RPM` 单位区分，不写「功率」「转速」文字；
- 底部为采样时间与实时标记，去掉了对用户无意义的流水序号。

**传输硬约束**：单张 GIF 必须 ≤ 24572 字节。调色板从 64 色提到 128 色并改用
Median Cut 才能保住渐变；160 色实测 24275 字节余量太小，192/256 色超限，
因此定在 128 色。用**实际传输 GIF 解码后**的图做预览，不用压缩前 RGB 图自欺。
数字字体缺 `≈` 字形会画成方框，近似符号改用中文字体单独绘制。
极值布局（100 °C、100 %、999 帧、9999 RPM、多口 200 W）逐项渲染无重叠，
GIF 约 21~22 KB。

**5 秒过期判定全程没有放宽**。此前三次「短观察窗口通过」的结论都因为随后
出现 5~7 秒空档被撤回，稳定性判据是「最长间隔」而不是中位数。

## 3. 真实风扇转速，不用控制百分比冒充

- CPU 风扇：主板 `Nuvoton NCT6687D` 的 CPU Fan 传感器，实测约 631 RPM；
- GPU 风扇：NVML 的 `nvmlDeviceGetFanSpeedRPM`，实测约 1001 RPM；
- 同一硬件上还有 CPU Fan 控制值 33 %、GPU Fan 控制值 30 %，
  **这两个百分比没有用于显示**。

## 4. 11-10：断网后屏幕不再显示「数据已过期」

### 根因不是路由器短时离线，是启动竞态

开机时登录触发的任务可能早于 Wi-Fi 完成连接。显示服务若写死绑定电脑的
局域网地址，启动瞬间该地址还不存在，会报 `WinError 10049`，任务以
错误码 1 退出，端口 18765 / 18766 都没有监听，屏幕只能进过期画面。

### 两层修法

1. **消除启动竞态**：两个服务都改为监听 `0.0.0.0`，不再要求开机瞬间
   已经拿到固定地址。Wi-Fi 稍后取得地址时，服务自然在该地址上可用，无需重启。
2. **持续自愈**：新增 `tools/screen_service_watchdog.py`，由计划任务每分钟
   用 `127.0.0.1` 检查两个端口；正常时什么都不做，端口消失就结束并重启
   对应任务，结果写入独立 JSONL 日志。用 `127.0.0.1` 是为了让路由器短时
   离线**不被误判**为电脑服务故障。

守护任务最初用 PowerShell 执行，会被 Windows Terminal 接管，每分钟弹一个
黑窗口；改用 `pythonw.exe` 无窗口执行后解决。恢复起来的采集子进程带
`CREATE_NO_WINDOW` 标志，也不弹窗。

### 实测证据

| 验收项 | 判据 | 结果 |
|---|---|---|
| 网络未就绪时启动 | 两个端口在没有局域网地址的情况下仍能监听 | 通过 |
| 网络恢复 | 拿到地址后无需重启服务即可从局域网访问 | 通过 |
| 服务意外退出 | 守护在下一次检查周期内自动恢复，退出码 0 | 通过 |
| 恢复后设备取图 | 两块屏请求间隔中位数约 1 秒，无过期提示 | 通过 |
| 原有回归 | 9 项自动测试全通过，新旧屏 GIF 都在 24572 字节上限内 | 通过 |

稳定性判据看「最长间隔」，不是中位数。

### ⚠️ 仍然存在的地址隐患

电脑当前地址由路由器动态分配（DHCP），**不是**系统静态地址，断网恢复后
不一定还拿到同一个地址。

没有擅自把 Windows 改成静态地址：无法确认路由器地址池范围，直接设可能造成
地址冲突。**正确做法是在路由器管理页建立 DHCP 固定租约**，把电脑网卡的
MAC 与固定内网地址绑定。重置或更换路由器后需要重新设置。

> 加载器固件里写死的是 `192.168.1.160`。地址变化时不要重刷设备，
> 先用 `tools/patch_firmware.py patch-url` 做等长替换，或恢复原地址。
> 详见 [10-常见问题.md](10-常见问题.md)。
